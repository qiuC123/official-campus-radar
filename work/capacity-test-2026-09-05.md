## 结论

尚未通过“2GB Linux 服务器同时承载网站和完整实时采集”的验收，不能据此保证采购后稳定运行。Windows 补充试验的内存没有触及限制，但并发访问明显变慢，且一个浏览器来源超时。此次不改变部署架构、不采购、不部署、不修改采集器。

## Linux 试验：采集中断，不能计为通过

- WSL2 Ubuntu、Python 3.13.15、Django 5.2.17、Gunicorn 26.2.0，2 个 sync worker。
- systemd/cgroup 对整个应用＋采集＋子进程组设 `MemoryMax=1536M`、`MemorySwapMax=0`、`CPUQuota=200%`，运行中回读控制文件确认限制生效。1.5GiB 应用预算是为 2GiB 机器预留约 0.5GiB 系统空间的试验假设，不是整机仿真。
- 时长 124.30 秒；8 次基线请求和 60 次并发阶段请求均成功；并发阶段 P95=2.5395 秒。
- cgroup 峰值内存 941,125,632 字节（约 897.5MiB），`memory.events` 中 max/oom/oom_kill 均为 0。
- WSL 将官网解析为 198.18.x.x Fake-IP，连续来源连接超时；只针对试验进程的独立 DNS 和公开 DoH 地址 hosts 检查仍未恢复拼多多连通性。未放宽公网 IP 校验、未绕过反爬或登录要求。
- 停止该轮采集（子进程退出 -15）；这是主动中止的网络受阻试验，不是全量运行成功或 OOM。

## Windows 补充试验：全来源尝试完成，但有失败及延迟

- 原本的 Python 3.13/Django 5.2.17 和官网采集代码；使用 Windows Job Object，在启动子进程前绑定进程组，聚合私有提交内存硬上限 1,610,612,736 字节，CPU affinity 为逻辑处理器 0、1；限制覆盖无头 Chromium 后代进程。
- 2 个独立单进程 wsgiref 服务模拟 2 个 Python Web worker；不是生产 Web 服务，不能当成云端 Gunicorn 的等价性能。客户端和测试协调器也在受限进程组中。
- Windows 提交内存不等于物理驻留内存或 Linux cgroup 总内存；Windows 主机自身仍有分页能力，本试验没有限制整机物理内存或关闭系统分页。

## 中国联通对照

完整试验结束后，同一原始适配器、同一副本配置，单独执行一次抓取和提取，不限制资源、没有并发网站负载，并通过 `PRAGMA query_only=ON` 禁止数据库写入：HTTP 200、1 个候选批次、42.41 秒，成功。

这说明来源不是持续不可用；但限制和负载同时改变，且只有一次对照，不能单独区分 CPU 竞争、页面加载时序和临时网络波动。未修改来源 timeout 或声称根因已确定。

## 部署判断与尚缺证据

内存占用支持继续评估 2GB，而不是证明必须购买 4GB。当前更明确的问题是采集并发时的页面延迟以及一次浏览器超时。下一步宜先分析/优化列表请求成本，随后在目标 Linux 环境复验完整采集与访问；未授权本轮实施这些优化。

尚未覆盖长期运行、更高并发、云 CPU 性能、磁盘/带宽限制、TLS/反向代理、备份进程或 PostgreSQL 共机。不能把当前 SQLite 试验外推为 PostgreSQL 容量保证，也不能把 2 个本机逻辑处理器外推为特定云实例性能。
