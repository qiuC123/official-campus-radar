> 2026-08-31 规则更新：本报告第 8 项记录的是当时的“公告地址不得作为投递回退”实现，该限制已由 ADR 0006 取代。当前允许公告入口与投递入口复用同一个已核验官方招聘页面；其余身份核验和公告准入结论不变。

## 审查结论

公告、岗位来源和投递入口已经拆成三个独立概念。官网正式公告或官方招聘系统项目页优先；只有官网候选经过语义审阅后仍没有合格公告，才把该企业交给 `wxcli` 补充微信候选。搜索结果、招聘首页、单个岗位页和搜索摘要都不能直接让批次进入正式页面。

项目所有者确认摘要 `fc27929cc6ecd9072f413745aecb35ecb1e95bfb68cf3369ab478e1f25ae20e0` 后，公告门控已于 2026-08-30（北京时间）开启。完成京东、腾讯、美团和大疆创新的逐项目官网补证后，正式页当前返回 13 家企业的 23 个已准入批次和 5719 个当前岗位；其余企业、旧批次和岗位均保留在本地数据库中，没有物理删除。

## 已发现并修复的高风险路径

1. 动态官网原始 HTML 没有关键词时，旧逻辑会误判“没有公告”。现在只标记为“内容待审阅”，不会直接触发微信回退或排除企业。
2. 对需要最终核验的动态官网，增加显式授权的一次性隔离浏览器渲染；它使用无痕上下文、不导入或保存日常浏览器 Cookie、阻止本地/私网字面地址，并重新检查最终跳转域名。动态页的原始 HTML 即使只有通用招聘词，也可在显式 `--force-browser` 授权下强制回读真实渲染正文；本轮腾讯、美团和北斗计划页面均按此路径完成核验。
   普通 HTTP 和隔离浏览器都失败时还可使用人工快照，但系统会单独记录 `human_snapshot` 方法、文件 SHA-256 和人工确认，所有批次字段定位都必须绑定该哈希，不能冒充实时官网回读。
3. 搜索命中的第三方 ATS 即使 URL 看起来合理，也必须先完成企业官网背书和来源准入；未准入来源不能生成已核验公告。
4. 增加“官网公告源”：它只证明集团官网公告身份，不参与岗位抓取，解决“公告在集团官网、岗位在另一招聘系统”的真实情况。
5. 微信公众号 `biz_id` 已配置时，正文读到不同 `biz_id` 不能再退回到“公众号名字相同”并误判为官方。
6. 微信候选输入拒绝未知字段、Cookie、认证头、密钥和值得怀疑的凭证赋值；浏览器权限只能来自显式 `--allow-browser`。
7. 招聘雷达会保存 `wxcli` 观察到的外链和图片/未来 OCR、二维码媒体证据，并只生成“待核验投递渠道候选”；不会自动访问或提升这些目标。
8. 投递入口不再回退到公告 URL。批次级邮箱、独立投递域名和没有稳定网页 URL 的微信小程序，都有独立的数据和验证路径。
9. 迁移预演现在按“切换门控后的真实字段归属”验证岗位投影，不能把只有公告但没有可信岗位/岗位方向和投递渠道的批次误报为可保留。
10. 正式查询明确只返回招聘中的批次；已结束的公告型批次进入历史查询。
11. 官网发现命令发生整体或分项失败时返回非零退出状态，自动化不能把失败 JSON 误当成功。
12. 增加显式“待处理批次”命令：只能关联同一企业的可信公告，不能进入正式页，也不能静默替换已经关联的主要公告。
13. 拼多多旧来源把职位类别字段当成职位标题，绿色的数量检查没有发现语义错误。现已修正来源目录和生成器，按审计链暂停、核验、重新启用来源，并只重采拼多多；重复执行修正命令不会追加伪审计事件。
14. 旧模型错误地要求同一来源的批次 URL 唯一，但现实中一个岗位门户会承载多个项目。现已保留“来源 + 项目身份”唯一约束，放宽门户 URL；只有配置了受审查分区的来源才允许多个候选共用门户，普通来源仍会把 URL 冲突判为歧义。
15. 分区抽取采用“互斥 + 穷尽”门槛：任一岗位被重复分配、出现未知项目编号或未被覆盖，整次来源更新失败并保留旧投影。项目编号由数字变成等值字符串时仍能正确匹配，避免 API 类型漂移把专项岗位误放入普通批次。
16. 对抗审查发现微信输入严格构造器此前没有接入命令路径。现在 `import_wxcli_announcements` 会在启动 wxcli 前重新执行完整字段白名单、凭证扫描、来源声明和 `mp.weixin.qq.com/s/` URL 校验；Candidate Batch 不能携带浏览器权限。
17. `RecruitmentBatch.objects.formal()` 原先在 QuerySet 链式过滤前立即遍历全部批次，并逐批查询公告、岗位和来源证据。现在详情端点先按批次 ID 缩小范围，首页门控批量预取并复用证据；当前本地实测首页约 24 次 SQL，单批次门控约 18 次 SQL。
18. 官网 HTTP 回读不再依赖请求库的自动重定向。每一跳会在请求发出前检查 HTTPS、已准入企业域名、凭证字段和 DNS 公网解析，最多允许 5 次重定向；最终地址仍会再次复核。
19. 分区配置和拼多多字段修正命令改为默认预演，只有显式 `--apply` 才写库。迁移预演命令默认只读，只有显式 `--record` 才保存后续门控确认需要的摘要。
20. 四个旧混合批次不是“待核验”，而是已经被 14 个精确项目完全替代的“已取代批次”。迁移 0024 将其标记为 `superseded`；来源继续更新新批次，但发布器会拒绝再次写入旧身份。
21. 人工快照哈希只用于证明字段定位关联了哪份人工材料，不是第三方防伪机制。门控现在会再次检查 locator 的快照哈希前缀；系统仍明确假设本地数据库和项目所有者可信。
22. 已保存的个人投递进度不再依赖批次继续出现在正式页；`/applications/` 提供独立查看和修改入口。
23. 公告门控激活新增追加式哈希审计事件；一旦开启，普通模型保存路径不能把开关改回关闭。管理员后台对策略和审计事件仍保持只读。

## 仍然存在的明确限制

- `wxcli 0.4.0` 已能回读微信正文、账号身份、图片 URL 和外链，但还没有图片 OCR、二维码解码或证据包；这些能力在 WxCLi 文档中规划为 0.6.0。因此图片型微信公告在当前集成中会保持“图片待核验”，不会被错误准入。
- 官网图片 OCR 也没有自动化。吉利等把届次写在宣传图里的页面要人工确认，或等待后续增加受控 OCR 证据类型。
- 截止日期只在来源明确给出时内部保存；页面不展示不稳定或大面积未知的截止时间。
- 四家共 14 个项目已经逐一保存官网项目证据并人工准入；这次准入不是由岗位接口自动触发，后续新增项目仍要重复相同门槛。
- 人工快照不会保存原始文件字节，因此只能提供哈希关联和防误用能力，不能证明材料未被拥有数据库写权限的人伪造。
- HTTP 逐跳检查会在请求前解析并拒绝非公网地址，但域名解析检查与底层连接之间仍存在很短的 DNS TOCTOU 窗口；在本地单用户、候选域名必须预先准入的边界下接受该剩余风险，不宣称已经实现网络层 IP 固定。
