## 本 Cycle 的目标

1. 修复 Cycle 05 暴露的字段证据误判：不得把数值 `JobAdId` 当岗位标题，支持嵌套字段并保留 `Category` 原值。
2. 对上汽大众、vivo 当前北森新版 Portal 做校招范围确认；有非空岗位的目标才执行两页验收。
3. 对中国电信执行一次安全的招聘单位选择，捕获真正岗位接口。
4. 不进入 T4，不写业务数据库，不重复失败请求。

## 离线补强

### 发现工具

- 北森字段明确映射为：`JobAdId`、`JobAdName`、`LocNames`、`ChangeDate/PostDate`。
- 支持从嵌套对象推断点路径字段。
- 纯数字或 UUID 形状的字段不能再被推断为岗位标题。
- `Category` 纳入校招/招聘类别原始证据。
- 新报告会保留候选数组实际条数和 `Count/rowCount` 的实际值，方便判断一次响应是否完整。

### JSON 适配器与地点规则

- 数组地点不再变成带方括号的 JSON 文本，改为用顿号连接。
- 地点规范化支持省市分隔符 `·`，并规范常见“省”后缀。
- 例如 `广东省·东莞市/深圳市` 会得到 `广东、东莞、深圳`，原始数组仍保留在字段证据中。

## 访问纪律

### 上汽大众

- 只打开一次当前 `/jobs` 页面，并安全点击一次可见的“校园招聘”导航。
- 最终官方分区为 `https://csvw.zhiye.com/campus/jobs`。
- 页面明确显示“全部职位（共 0 个）”，因此没有发送两页 API 请求；空列表不能构成非空校招来源证据。

### vivo

- 使用 Cycle 05 已观察到的精确秋招请求体，不再打开页面。
- 只发送 `PageIndex=0` 和 `PageIndex=1` 两个最简 JSON 请求，间隔 1 秒，无 Cookie、无重试。
- 只保存允许字段和岗位 ID，不保存完整响应。

### 中国电信

- 先只读确认当前校园招聘页有“招聘单位(44)”以及唯一的“中国电信北京公司”列表项。
- 正式发现调用只执行一次：1 次初始导航、1 次非表单同页点击、无滚动、无 reload。
- 捕获后的岗位接口执行固定 5 级请求头重放，停在 `5/6`；没有重复运行发现命令。

## 结果

### vivo：通过

接口：`POST https://hr-campus.vivo.com/api/Jobad/GetJobAdPageList`

- 最简无 Cookie 请求返回 HTTP 200 JSON。
- 请求原始筛选：`ClassificationOne: ["2"]`，可见页面标签为“秋季校园招聘”。
- 第 0、1 页各 20 条，总数均为 137；两页岗位 ID 完全不重复。
- 样本字段完整：`JobAdId`、`JobAdName`、`LocNames`。
- 响应原值同时给出 `Category: 校园招聘`、`CategoryId: 2`。
- 标题明确含“27届秋招”，地点覆盖东莞、深圳、上海、南京、杭州等。
- `ChangeDate` 有真实值；`PostDate` 的 `0001-01-01` 哨兵值不作为更新时间。

因此 vivo 同时满足官方证据、最简非空、校招原值、标题地点、分页五项条件，稳定来源累计从 3 家增加到 4 家。

### 上汽大众：当前无非空校招来源

当前北森 Portal 架构清楚，但官方校园招聘分区显示 0 个职位。Cycle 05 的 93 个岗位属于社会招聘，不能挪作校招数据，也不能计入稳定来源。

### 中国电信：接口确认，仍缺完整性证明

接口：`POST https://job.chinatelecom.com.cn/wt/TELE/web/mode400/position/list`

- 点击“中国电信北京公司”后成功触发岗位接口，最终仍为中国电信当前校园招聘站内路由。
- 捕获请求体为 `{}`，最简无 Cookie 请求可返回等效非空列表。
- 列表路径为 `data.details`，总数字段为 `data.rowCount`。
- 字段完整：`PostId`、`PostName`、`WorkPlace`、`ReleaseTime`。
- 样本均有 `RecruitType: 1`、`RecruitTypeName: 校园招聘`，地点为北京市。
- 本次旧版报告格式没有保存候选数组条数和 `rowCount` 实际值；请求体也没有页码字段。

因此尚不能判断空正文是否一次返回全部岗位，也不能证明分页规则。不得猜页码参数，中国电信本轮不增加稳定计数。
