# Phase 02 正式页面性能 Cycle 01

日期：2026-08-27

## 问题

正式首页每次刷新都会重新核验来源和字段证据。当前数据库有 25 个招聘批次、7398 个当前岗位；旧实现为每个待核验字段从整批证据中线性查找对应项，岗位增加后形成大量重复比较。

## 修改

在单个招聘批次的证据核验开始时，按 `字段名 + 岗位 ID + 投递链接 ID` 建立内存索引。后续仍调用原有 `field_evidence_matches` 完成原值、解析值、定位信息和值哈希校验，只把“寻找对应证据”的方式从反复扫描改为直接索引。

本轮没有跳过证据核验，没有缓存跨请求的准入结果，也没有修改数据库数据。

## 性能结果

测试条件：本地 SQLite，25 个批次、7398 个当前岗位，Python 3.13。

| 场景 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 全部正式岗位后端组装 | 5.319 秒 | 1.271 秒 |
| 2027 届筛选后端组装 | 5.386 秒 | 1.293 秒 |
| 民企 + 央国企 + 2027 届 | 5.543 秒 | 1.241 秒 |
| 同一筛选的完整 HTTP 请求 | 5.624～6.091 秒 | 1.243～1.418 秒 |
| 浏览器实际刷新 | — | 1.484 秒 |

数据库查询数仍为 118 次，但分析显示主要耗时已经从约 4100 万次重复证据比较中移除；查询进一步合并可作为后续优化，不影响本 Cycle 的正确性。

## 验收

- 证据篡改、岗位/链接篡改和准入链相关测试继续通过。
- 正式页面返回相同批次和岗位数量。
- 本地浏览器刷新后页面可正常显示。
