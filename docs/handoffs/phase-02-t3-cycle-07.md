# Phase 02 / T3 Cycle 07 中国电信完整性复核与下一组发现

日期：2026-08-27

状态：已完成；美团满足 H3 五项条件，新增稳定接入 1 家，累计更新为 5/50

## 本 Cycle 的目标

1. 用一次最简请求核对中国电信空正文响应是否已返回完整岗位列表。
2. 从冻结的 50 家企业池继续探测 OPPO、美团、亚马逊中国和中国工商银行。
3. 只在参数已有明确证据时补分页验证，不猜请求参数、不重复失败请求。
4. 不进入 T4，不写业务数据库，不启动生产浏览器采集。

## 访问纪律

- 中国电信完整性检查只发送一次 `POST {}`，无 Cookie、无重试。
- 下一组发现工具只运行一次；4 个目标各打开一次页面、无点击、无滚动。
- 每个候选端点的重放上限为 6 次。发现工具的完整五级最简头验证占 5 次；同一端点只允许剩余 1 次做分页证据。
- OPPO 请求含 `Authorization`，因此未重放、未尝试移除或逆向。
- 美团参数已经由浏览器捕获明确给出 `page.pageNo`，才使用第 6 次也是最后一次请求取得第 2 页。
- 原始响应不落盘；报告只保留岗位 ID 和允许字段。

## 结果

### 中国电信：接口非空，但列表不完整

接口：`POST https://job.chinatelecom.com.cn/wt/TELE/web/mode400/position/list`

- 最简无 Cookie 的空 JSON 正文返回 HTTP 200 JSON。
- `data.details` 只有 10 条，而 `data.rowCount` 为 2935，证明空正文只是第一页或截断列表，不是完整列表。
- 10 条岗位 ID 唯一；岗位标题、地点、发布日期完整，`RecruitTypeName` 原值均为“校园招聘”。
- 捕获正文仍没有页码参数，因此禁止猜测分页字段。

中国电信继续保持候选，不增加稳定计数。

### 美团：通过

接口：`POST https://job.meituan.com/api/official/job/getJobList`

- 官网招聘入口直达当前校园招聘页面。
- 五级重放已证明最简 JSON 头、无 Cookie 可以返回非空列表。
- 捕获正文明确包含 `page.pageNo` 和 `page.pageSize`；第一页报告保存了岗位 ID。
- 第 6 次最终请求使用 `pageNo: 2`，返回 10 条岗位，报告总页数为 57。
- 第 2 页 10 个 ID 内部唯一，并与第一页保存的 5 个抽样 ID 完全不重叠。
- `jobType` 原值包含 `2`，样本标题为实习岗位；`name` 和 `cityList` 均完整。

因此美团满足官方证据、最简非空、实习原值、岗位标题地点、分页规则五项条件，稳定来源累计从 4 家增加到 5 家。

### OPPO：有岗位接口，但含授权头

- 观察到 `POST /openapi/position/pageNew`，列表为 `data.records`，当前 10 条、总数 239。
- 岗位 ID、标题、地点和更新时间字段清楚。
- 捕获请求含 `Authorization`，安全规则要求不重放、不移除、不逆向。

OPPO 不能证明匿名最简请求可用，继续保持不稳定。

### 亚马逊中国：通用岗位接口可读，但校招范围和总数不可靠

- `GET /en/search.json` 使用最简无 Cookie 请求可返回中国岗位，列表路径为 `jobs`。
- 当前响应混有普通全职岗位；`is_intern` 在抽样岗位中均为 `null`，只有个别标题含 `Intern`，不足以形成可靠的校招/实习字段规则。
- 工具误把分类 facet 中的数字 6 推断成岗位总数，但当前列表已有 10 条，明显不是正确总数字段。
- `offset` 参数虽已观察到，但在校招范围和真实总数未确认前不消耗最后一次端点请求。

亚马逊中国继续保持候选，且本次保留“总数误推断”作为发现工具后续修复项。

### 中国工商银行：捕获的是招聘公告，不是岗位列表

- 校招、社招和暑期实习公告接口均能在浏览器内观察到，但返回行是公告标题，不是具体岗位。
- 最简重放因站点旧 TLS 协商失败，没有得到等效非空响应。
- 另有岗位类型字典候选，但它也不是岗位明细列表。

中国工商银行不增加稳定计数，禁止把批次公告伪装成岗位。
