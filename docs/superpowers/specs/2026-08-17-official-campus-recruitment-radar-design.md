# 官方校招信息雷达 V0 设计

状态：已确认；实施计划待用户审阅

日期：2026-08-17

## 1. 问题与目标

求职者缺少的不是零散招聘消息，而是及时、可核验、能直接行动的官方校招信息。本项目将企业官网招聘页和已核验的官方招聘公众号作为唯一正式来源，自动汇总北上广深岗位，并在本地提供可筛选的投递信息表。

V0 的目标是一个仅供项目所有者在 Windows 电脑上使用的本地应用。它每天自动检查已核验来源，自动发布满足规则的新增或变更信息，并保留个人投递进度。

## 2. 已确认的产品决策

- 使用范围：仅供项目所有者本机使用；不做登录、多人协作或公开部署。
- 更新频率：每天北京时间 22:00 自动更新一次。
- 漏跑处理：电脑关机或休眠导致错过任务时，不伪造成功记录；用户下次打开应用时显示未完成提醒，并提供“立即更新”。
- 目标岗位：以岗位工作地点是否包含北京、上海、广州或深圳为准，不以企业总部所在地判断。
- 企业范围：互联网/科技大厂（以腾讯、阿里同类企业为起点）、央企与国企。系统先建立候选企业池；只有找到并核验官方来源后才纳入日常监控。
- 正式来源：企业官网招聘页，以及已核验的企业官方招聘公众号公开文章。招聘平台、论坛、群消息和转载只能作为发现线索，不能作为发布证据。
- 发布方式：自动发布，但必须通过确定性来源、内容、地点和去重规则；规则不通过的内容不得进入正式列表。
- 总公司与分公司：前台按实际招聘主体分别展示，不展示集团标签；后台仅用组织关系辅助去重和统计。
- 前台形态：采用可选择显示列的横向筛选表。
- 个人投递进度：保留并仅由用户手动修改，固定状态为 `未投递`、`已投递`、`已笔试`、`已面试`、`已挂`、`面试通过`、`暂不投递`。
- 不纳入 V0：笔试情况、公司规模、社区经验信息、云服务器、自动投递、简历与账号数据。

## 3. 来源与自动发布规则

### 3.1 来源准入

一个来源只有同时满足以下条件才能进入来源白名单：

1. 能证明其属于企业官网，或能证明其是该企业官方招聘公众号；
2. 提供稳定的入口 URL；
3. 可在不登录、不绕过验证码、不伪装身份和不突破访问限制的前提下低频访问；
4. 记录来源核验依据、访问策略和最近一次健康状态。

由企业官网直接跳转到招聘系统（例如第三方 ATS）时，该跳转可作为官方投递入口；没有来自官网的证据链时，第三方招聘系统不得单独作为正式来源。

### 3.2 自动发布门槛

候选内容只有同时通过下列规则才自动发布：

```text
来源在白名单内
+ 存在官方原文 URL
+ 内容明确属于招聘、校招或实习
+ 已提取到北上广深的岗位工作地点
+ 与已有公告或岗位不重复
= 自动发布
```

官方公告未给出投递入口时，仍可作为“招聘公告”发布，但页面必须明确显示未提供官方投递链接；系统不得猜测或补造链接。

AI 如在后续使用，只能协助文本提取、分类和冲突提示。官方性、URL、日期和发布条件必须由规则和证据校验决定。

## 4. 信息生命周期

```text
已核验来源
  → 定时抓取
  → 页面版本与变更检测
  → 字段提取和规则校验
  → 新增 / 更新 / 不发布
  → 有效列表
  → 已截止 / 已撤回 / 来源异常历史
```

- 新官方公告：创建正式记录。
- 同一公告内容变化：更新原记录并保留最近核验时间。
- 截止日期已过，或官方原文明确结束：从有效列表移到已截止历史。
- 官方明确撤回：标记为已撤回，保留证据。
- 来源访问失败：保留原记录，标记来源异常；不得自动判为已截止或删除。
- 不满足发布规则：记录为内部异常，不能污染正式列表。

历史记录不做物理删除。这样既保留可追溯证据，也能避免一次抓取异常造成误删。

## 5. V0 数据模型

| 实体 | 核心字段 | 责任 |
| --- | --- | --- |
| `organizations` | 名称、别名、公司类型、行业、官网域名、可选父组织 | 规范企业与招聘主体身份 |
| `official_sources` | 企业、来源类型、入口 URL、核验依据、访问策略、状态 | 维护正式来源白名单 |
| `fetch_runs` | 来源、执行时间、结果、错误、耗时 | 发现任务失败，避免静默失效 |
| `source_versions` | 来源、规范 URL、内容哈希、抓取时间、ETag/版本信息 | 检测页面是否变化 |
| `recruitment_notices` | 企业、标题、招聘类型、招聘对象、发布时间、截止时间、状态、首次发现/最近核验时间 | 表示一则官方招聘公告 |
| `notice_positions` | 公告、岗位名称、工作地点、岗位原文 | 表示公告中的可投岗位 |
| `application_links` | 公告或岗位、投递 URL、链接类型、验证时间 | 保存有证据链的官方投递入口 |
| `application_progress` | 公告或岗位、用户状态、最近修改时间 | 保存个人投递状态，不受采集器改写 |
| `evidence` | 对象、字段名、原文摘录、页面版本、定位信息 | 证明显示字段来自何处 |

V0 前台列为：公司名称、公司类型、所属行业、招聘类型、招聘对象、工作地点、岗位、投递进度、更新时间、投递截止、官方投递链接、官方招聘公告、备注。笔试情况与公司规模不建模为正式展示字段。

## 6. 本地架构

```text
本地浏览器页面
        ↓
Python / Django 单体应用
  ├─ 目录查询与投递进度
  ├─ 来源管理
  ├─ 采集、变更检测和校验
  └─ 本地更新状态与提醒
        ↓
SQLite 数据库
        ↑
Windows 任务计划（每天 22:00） → 采集命令 → 独立来源适配器
```

推荐采用 Python、Django、SQLite、Windows 任务计划和按来源分离的适配器。公开静态页面优先用低频 HTTP 访问；仅在页面确实需要浏览器渲染且站点允许时，才使用受控浏览器自动化。V0 不引入微服务、消息队列、云数据库或工作流平台。

来源适配器不得把网页 HTML 结构泄漏到业务查询层；页面、采集、去重、发布和个人进度应通过清晰的应用服务边界协作。

## 7. 失败处理与隐私边界

- 单个来源失败不会中断其他来源，也不会删除已有招聘记录。
- 每次更新必须记录执行结果和最近成功时间。
- 应用打开时，将当天预期更新时间与最近成功记录比较；若 22:00 任务漏跑或失败，显示提醒和“立即更新”入口。
- 不存储简历、身份证明、企业登录凭据、浏览器 Cookie 或投递账号。
- 不登录、不绕过验证码、不使用代理池、不规避反爬措施。
- 对外部网页仅低频访问，并遵守其条款、访问频率和 `robots.txt`（如适用）。

## 8. 验收标准

V0 完成时，必须能够证明：

1. Windows 任务可在北京时间 22:00 调用更新命令；任务成功和失败均写入本地记录。
2. 对已配置来源，未变化页面不产生重复公告；发生真实变化时仅更新对应记录或创建一个新记录。
3. 正式列表只展示工作地点包含北上广深、且带官方原文 URL 的记录。
4. 截止和撤回状态不会物理删除历史；来源抓取失败也不会把招聘信息误判为已截止。
5. 用户可筛选表格、显示或隐藏列、打开官方公告或投递入口，并手动更新自己的投递进度。
6. 电脑错过 22:00 更新后，应用能显示漏跑提醒，并允许用户手动发起一次更新。
7. 自动化测试覆盖来源校验、去重、状态迁移、地点筛选、投递进度隔离和漏跑判定；手工验收覆盖 Windows 定时任务与本地网页交互。

## 9. 明确延期事项

- 部署到云服务器并在电脑关机时仍准时运行；
- 多用户、账号、权限、公开访问和通知推送；
- 小红书、B 站等社区信息与笔试经验模块；
- 大规模全网企业发现、复杂队列和分布式采集；
- 自动填写或提交任何招聘申请。

上述事项只有在 V0 稳定运行、来源覆盖与更新质量达到预期，并得到用户新的明确批准后，才进入后续阶段。
