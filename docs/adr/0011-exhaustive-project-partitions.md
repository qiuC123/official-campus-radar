# ADR 0011：多项目岗位门户采用无预筛选抓取与穷尽分组

状态：已接受

日期：2026-09-03

## Context

vivo 官方招聘页同时提供蓝极星计划、秋季校园招聘、日常实习生和暑期实习生四个招聘项目，但原来源请求固定携带 `ClassificationOne=["2"]`，只抓取秋季校园招聘。页面上的校园招聘与实习生招聘筛选都真实存在，系统却因为请求前已经缩小范围，无法发现另外三个项目，因此正式页只显示一个批次。

这类漏数不能靠增加前端筛选项解决。只要采集请求预先指定了已知项目，官网以后新增项目时，接口仍会成功返回旧项目，系统也会继续静默漏掉新项目。

## Decision

对能在岗位响应中返回稳定项目字段的官方接口，采用一次无项目预筛选的完整抓取，再按该字段映射为互斥批次：

- 请求中的项目字段必须显式为空列表，不能只请求当前已知项目。
- 每个已审核批次必须用同一个响应项目字段和非空的精确值集合分组，各批次值不得重叠。
- 完整抓取中的每个保留岗位必须且只能归入一个分组；出现未覆盖值或重复归属时，整次来源更新失败，不发布部分结果。
- 未知项目保留在失败诊断中，由人工核验其批次身份、招聘类型和招聘对象后再新增分组；系统不得自动创建正式批次或归入“其他”。
- 官网导航筛选用于发现项目；正式准入仍需要官方项目身份、字段证据和当前岗位回读。

vivo 首个采用该契约：一次抓取四个项目的完整岗位集合，再按响应中的 `ClassificationOne` 文本分成蓝极星计划、秋季校园招聘、日常实习生和暑期实习生四个批次。已有秋季批次身份保持不变，因此用户投递进度不会丢失。

## Consequences

- 官网新增带岗位的项目时，系统会显式报错，而不是继续显示“更新成功”却漏掉项目。
- 一次完整请求比为每个项目分别请求更省资源，也能把官网当前项目全集作为覆盖基线。
- 官网更改项目字段或名称会触发失败，需要人工更新配置；这是避免误分类的有意选择。
- 该机制只适用于响应含稳定项目字段且接口能无筛选返回完整集合的来源。其他来源仍需按其官方契约设计，不能强行套用。

## Rejected alternatives

- 为当前四个项目各发一次过滤请求：能补齐眼前数据，但未来新增第五个项目仍会静默漏掉，并增加请求次数。
- 给未识别岗位设置“其他”兜底批次：会在没有证据时猜测批次语义和招聘对象。
- 仅定期视觉检查官网筛选项：可以辅助发现变化，但不能证明岗位数据已完整进入每个批次，也不能替代机器可执行的覆盖校验。
